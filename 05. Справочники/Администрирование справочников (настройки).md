# Администрирование справочников (раздел «Настройки»)

> Задача поставлена пользователем (Сергеем) в чате, не из [[Заметки на будущее|заметок]]. **Статус: ✅ реализовано** (коммит `c499a6f`). Ниже сохранено исходное ТЗ, по которому делалась реализация; отклонения от него перечислены в разделе «Реализовано» в начале документа.

## Реализовано

Модуль `app/services/reference_admin.py` — декларативный реестр `REFERENCE_REGISTRY`
(подразделения, валюты, компании-покупатели, агенты, типы документов), как и предлагалось
в ТЗ; отдельные страницы на каждый справочник не создавались.

Роуты (все — `_require_analytics_access`: Руководитель, Исполнитель, действующий делегат;
Заказчику закрыто):

| Роут | Назначение |
|---|---|
| `GET /settings/references` | экран 1 — список справочников с количеством записей |
| `GET /settings/references/{key}` | экран 2 — записи одного справочника |
| `GET /settings/references/{key}/new`, `POST .../create` | добавить запись |
| `GET /settings/references/{key}/{pk}/edit`, `POST .../update` | изменить запись |
| `POST /settings/references/{key}/{pk}/delete` | удалить одну |
| `POST /settings/references/{key}/bulk_delete` | удалить несколько (чекбоксы) |

Кнопка «CSV» на экране 2 ведёт на существующий `/settings/import?reference={key}` —
импорт не дублировался.

Решения, которые ТЗ оставляло на усмотрение разработчика:
- **вариант массового удаления** — «мягкий»: удаляется всё незанятое, занятые записи
  не удаляются и перечисляются в сообщении (для справочников с `is_active` — деактивируются);
- **правка** — отдельная страница-форма (`.../edit`), а не инлайн/модалка;
- **проверка использования** — для агентов учитываются обе роли (агент и субагент, включая
  предложения условий), для валют — заявки, фактические исполнения и кэш курсов,
  для типов документов — загруженные документы и переопределения требований.

Аудит: `REFERENCE_CREATED`, `REFERENCE_UPDATED` (по каждому изменённому полю, old→new),
`REFERENCE_DELETED`; `entity_type = reference:<ключ справочника>`. Для типов документов
(текстовый первичный ключ) код сохраняется в `field_name`, `entity_id = 0` — иначе после
удаления записи её не опознать. Значения добавлены миграцией `c4d5e6f7a8b9` (append-only).

CSV-импорт (коммит `27e5938`) покрывает все пять справочников: `import_agents`,
`import_buyer_companies`, `import_exchange_rates`, а также дописанные `import_divisions`
(CSV `name`) и `import_document_types` (CSV `code,name,category,is_required_default,recipient_service`;
`category` принимает и технические значения, и русские подписи). Импорт по-прежнему только
добавляет и обновляет — удаление не поддерживается, это делается вручную в UI.

Его нельзя редактировать через CRUD-страницу без изменения кода и миграции — если нужно сделать его управляемым справочником, это отдельная, более серьёзная задача (перевод enum в таблицу БД со всеми зависимыми местами, где он используется — `PaymentTermsProposal.proposed_payment_method`, `PaymentExecution.method`). Ниже эта задача не включена в scope, но отмечена как отдельный пункт на будущее.

### Что уже есть для импорта (переиспользовать, не дублировать)
`app/services/import_refs.py` + роут `POST /settings/import` (форма на `settings/import.html`) — на сегодня умеет **upsert по ключу** (добавить новое / обновить существующее по коду или имени) для: `import_agents`, `import_buyer_companies`, `import_exchange_rates`. **Нет** `import_divisions` и `import_document_types` — при реализации этой задачи стоит дописать и их, по той же сигнатуре `(db: Session, file: BinaryIO) -> dict`, для единообразия. Удаления через CSV-импорт нет и не должно появляться (риск случайно затереть справочник пустым/неполным файлом) — удаление только через явный UI, см. ниже.

## Предложение по архитектуре (рекомендуемый вариант)

Вместо пяти отдельных вручную написанных страниц (по одной на справочник) — **одна универсальная CRUD-страница**, параметризованная ключом справочника. Обоснование: все пять справочников — плоские таблицы из 2–6 простых полей (строка/bool), логика просмотра/редактирования/удаления/bulk-удаления для них идентична, разница только в наборе колонок. Отдельные страницы на каждый справочник — это 5x дублирование одного и того же кода ради косметики; при появлении шестого справочника (а судя по `AGENTS.md`/`Agent`-докстрингу — «полное расширение справочника агентов запланировано отдельно» — новые поля/справочники будут появляться) его придётся снова писать с нуля.

### Реестр справочников
Новый модуль `app/services/reference_admin.py` с декларативным реестром:
```python
from dataclasses import dataclass, field
from typing import Any, Callable

@dataclass
class ReferenceField:
    name: str
    label: str
    type: str  # "str" | "bool" | "enum"
    editable: bool = True
    required: bool = False

@dataclass
class ReferenceSpec:
    key: str                    # "agents", "buyer_companies", "divisions", "currencies", "document_types"
    label: str                  # "Платёжные агенты"
    model: type
    pk_field: str                # "id" или "code" (для DocumentType)
    fields: list[ReferenceField]
    import_fn: Callable | None = None     # существующая import_agents и т.п., None если ещё не написана
    usage_check: Callable[[Session, Any], int] | None = None  # считает, сколько Request/RequestDocument ссылаются на запись

REFERENCE_REGISTRY: dict[str, ReferenceSpec] = {
    "divisions": ReferenceSpec(
        key="divisions", label="Подразделения", model=Division, pk_field="id",
        fields=[ReferenceField("name", "Название", "str", required=True)],
        usage_check=lambda db, obj: db.query(Request).filter(Request.division_id == obj.id).count(),
    ),
    "currencies": ReferenceSpec(
        key="currencies", label="Валюты", model=Currency, pk_field="id",
        fields=[ReferenceField("code", "Код (ISO 4217)", "str", required=True)],
        usage_check=lambda db, obj: db.query(Request).filter(Request.currency_id == obj.id).count(),
    ),
    "buyer_companies": ReferenceSpec(
        key="buyer_companies", label="Компании-покупатели", model=BuyerCompany, pk_field="id",
        fields=[
            ReferenceField("name", "Название", "str", required=True),
            ReferenceField("is_active", "Активна", "bool"),
        ],
        import_fn=import_buyer_companies,
        usage_check=lambda db, obj: db.query(Request).filter(Request.buyer_company_id == obj.id).count(),
    ),
    "agents": ReferenceSpec(
        key="agents", label="Платёжные агенты", model=Agent, pk_field="id",
        fields=[
            ReferenceField("code", "Код", "str", required=True),
            ReferenceField("name", "Название", "str"),
            ReferenceField("is_resident", "Резидент", "bool"),
            ReferenceField("is_active", "Активен", "bool"),
            ReferenceField("is_own_company", "Наша компания", "bool"),
        ],
        import_fn=import_agents,
        usage_check=lambda db, obj: (
            db.query(Request).filter(or_(Request.agent_id == obj.id, Request.subagent_id == obj.id)).count()
        ),
    ),
    "document_types": ReferenceSpec(
        key="document_types", label="Типы документов", model=DocumentType, pk_field="code",
        fields=[
            ReferenceField("name", "Название", "str", required=True),
            ReferenceField("category", "Категория", "enum", required=True),
            ReferenceField("is_required_default", "Обязателен по умолчанию", "bool"),
            ReferenceField("recipient_service", "Служба-получатель", "str"),
        ],
        usage_check=lambda db, obj: db.query(RequestDocument).filter(
            RequestDocument.document_type_code == obj.code
        ).count(),
    ),
}
```
Это не предписание дословного кода (конкретные импорты/сигнатуры могут отличаться) — предписание **подхода**: один реестр, одна страница, вместо пяти копипаст-страниц.

### Роуты (доступ — Руководитель, действующий делегат и Исполнители отдела: проверка `_require_analytics_access`; Заказчику закрыто. Управление делегированием — по-прежнему только Руководитель, `_require_rukovoditel`)
- `GET /settings/references` — список справочников из реестра с количеством записей в каждом (карточки/таблица со ссылками).
- `GET /settings/references/{key}` — таблица записей выбранного справочника: все поля из `fields`, чекбокс в начале строки, колонка «Используется в N заявках» (из `usage_check`), кнопка «Редактировать» на строку, кнопка «Добавить запись».
- `POST /settings/references/{key}/create` — создать новую запись (валидация `required`-полей на сервере).
- `POST /settings/references/{key}/{pk}/update` — обновить запись.
- `POST /settings/references/{key}/{pk}/delete` — удалить одну запись.
- `POST /settings/references/{key}/bulk_delete` (`ids: list[str] = Form(...)`) — удалить несколько отмеченных записей за один запрос/одну транзакцию.
- CSV-загрузку **не дублировать** новым роутом — на странице `/settings/references/{key}` достаточно ссылки/кнопки на существующий `/settings/import` с предвыбранным `reference={key}` (добавить таким образом, чтобы `import.html` принимал параметр предвыбора через query-string).

### Защита от удаления используемых записей (обязательно, иначе легко сломать исторические заявки)
Перед любым `delete`/`bulk_delete`:
1. Вызвать `usage_check(db, obj)` для каждой записи.
2. Если результат > 0 — **запретить** удаление этой записи (вернуть ошибку с текстом «Запись используется в N заявках, удаление запрещено»); для справочников с полем `is_active` (`Agent`, `BuyerCompany`) в этом случае предложить вместо удаления деактивировать (`is_active = False` — запись перестаёт предлагаться при создании новых заявок, но не ломает исторические).
3. Для `DocumentType` и `Division`/`Currency` (у которых нет `is_active`) — при попытке удалить используемую запись рекомендация такая же (запретить), но деактивации для них сейчас не предусмотрено: если это часто будет возникать на практике — отдельной задачей добавить `is_active` и этим справочникам (сейчас не добавляю, чтобы не расширять scope без необходимости — Руководитель может решить, что это не нужно, т.к. состав типов документов/валют/подразделений меняется редко).
4. Bulk-удаление — транзакционно: либо удаляются все отмеченные незанятые записи и по занятым выводится отдельный список «не удалено, т.к. используется», либо (более строгий вариант) всё удаление отменяется, если хотя бы одна из отмеченных записей занята, и явно показывается, какая — **выбор одного из двух вариантов — на усмотрение разработчика/Руководителя, в заметке зафиксировать, какой выбран**.

### Аудит
Новые значения `AuditActionType`: `REFERENCE_CREATED`, `REFERENCE_UPDATED`, `REFERENCE_DELETED` — пишутся в `AuditLog` с `entity_type=<ключ справочника>`, `entity_id=<pk>`, `field_name`/`old_value`/`new_value` для `update` (по аналогии с тем, как уже логируются другие действия в [[Аудит]]). Сейчас изменения справочников вообще нигде не логируются (ни текущий импорт, ни единственный существующий `toggle_document_requirement` для них) — это тоже закрывается данной задачей.

## UI / визуальное решение

**Принцип: два экрана, не одно перегруженное окно.** В любой момент на экране виден либо список справочников (без содержимого), либо содержимое ровно одного справочника — никогда все пять сразу. Это прямой ответ на риск «перегрузки интерфейса»: пять таблиц разных справочников на одном окне действительно были бы нечитаемы (суммарно порядка 43 строк — 3+9+7+4+20 — плюс разные наборы колонок у каждой), поэтому они физически разнесены на разные экраны/URL, а не сворачиваются в аккордеон на одной странице.

### Экран 1 — `GET /settings/references` (список справочников)
Пункт меню в разделе «Настройки»: «Справочники», рядом с существующим «Импорт».

Вертикальный список карточек, одна строка на справочник, без содержимого самих записей:
```
┌─────────────────────────────────────┐
│ ⚙ Настройки → Справочники            │
├─────────────────────────────────────┤
│ 🏢  Подразделения                 3 →│
│ 💰  Валюты                        9 →│
│ 🏬  Компании-покупатели           7 →│
│ 👥  Платёжные агенты              4 →│
│ 📄  Типы документов              20 →│
└─────────────────────────────────────┘
```
Каждая строка: иконка + название справочника + количество записей (просто `COUNT(*)`, без выборки самих записей — экран лёгкий, ничего лишнего не грузит) + стрелка-переход. Клик по строке → экран 2 для этого справочника. Больше на этом экране ничего нет — ни полей, ни кнопок редактирования.

### Экран 2 — `GET /settings/references/{key}` (содержимое одного справочника)
Открывается по клику с экрана 1, параметр `{key}` — какой именно справочник (`agents`, `currencies`, `divisions`, `buyer_companies`, `document_types`). На экране — только записи этого справочника:
```
┌─────────────────────────────────────┐
│ ← Платёжные агенты        [CSV][+]   │
├─────────────────────────────────────┤
│ ☐ ТиР (наша компания) (ТиР)       ✎ │
│     резидент · своя компания         │
│ ☐ Али (Али)                       ✎ │
│     нерезидент                       │
│ ☐ А (А)                           ✎ │
│     резидент                         │
│ ☐ Эп (Эп)                         ✎ │
│     нерезидент · неактивен           │
├─────────────────────────────────────┤
│ ☐ Выбрать все      Удалить (0)      │
└─────────────────────────────────────┘
```
- **Шапка**: стрелка «назад» к экрану 1, название справочника, две кнопки — «CSV» (переход на `/settings/import?reference={key}` — существующая страница импорта с предвыбранным справочником, см. ниже) и «+ Добавить» (новая запись).
- **Строка записи**: чекбокс слева, основные поля (для агента — код и название), под ними серым — второстепенные поля в одну строку через « · » (резидент/нерезидент, своя компания, неактивен), карандаш справа — открывает редактирование этой записи (инлайн или модалка, см. «После реализации» ниже — решение за разработчиком). Для справочника с другим набором полей (например «Типы документов») состав второстепенной строки меняется под `fields` из реестра — сама структура карточки-строки одна и та же для всех пяти справочников, меняется только содержимое.
- **Низ экрана**: «Выбрать все» слева, кнопка «Удалить (N)» справа — неактивна (серая), пока не отмечена ни одна строка; при отметке хотя бы одной — активируется и показывает счётчик. Это единственное место массового действия — никакого глобального «удалить всё» по всем справочникам сразу не существует, удаление всегда в контексте одного открытого справочника.
- Если запись отмечена, но используется в заявках (см. «Защита от удаления» выше) — при попытке удалить она явно остаётся в списке с пояснением «используется в N заявках, не удалена», а не исчезает молча.

### Про CSV — отдельно, чтобы снять второе опасение
Кнопка «CSV» на экране 2 ведёт **не на какой-то новый универсальный импортёр «для всех справочников сразу»**, а на уже существующую страницу `/settings/import`, у которой уже сегодня есть выпадающий список «какой справочник» и под каждым пунктом списка — своя функция импорта со своим форматом колонок CSV (`import_agents` ждёт `code,name,is_resident,is_active,is_own_company`; `import_buyer_companies` — `name,is_active`; и т.д., см. «Что уже есть для импорта» выше). Единственное изменение здесь — страница `/settings/import` при переходе с кнопки «CSV» экрана 2 открывается с уже выбранным в выпадающем списке нужным справочником (через `?reference={key}` в URL), чтобы не выбирать его второй раз руками. Импорт как был, так и остаётся раздельным по справочникам — просто вызывается из двух мест (общий пункт меню «Импорт» и кнопка на экране конкретного справочника), а не дублируется.
