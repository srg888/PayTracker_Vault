# Аналитика и контроль работы с агентами (валютный контроль)

> Источник: поставлена пользователем (Сергеем) в чате. **Статус: ✅ реализовано** (код `srg888/paytracker`, коммит `dde0177`) — в разрезе **договоров** агента, а не агента в целом (уточнение пользователя после первой версии ТЗ: у одного агента может быть несколько договоров, учёт и пороги 173-ФЗ — по каждому договору отдельно).

## Отдельный раздел «Агенты» (не часть «Настройки → Справочники»)

Новый пункт меню «// АГЕНТЫ» (`/agents`), виден Руководителю и всем Исполнителям (та же видимость, что у «Отчёты»/«Аудит»/«Настройки» — `_require_analytics_access`). Назначение разделено:
- `/settings/references/agents` ([[Администрирование справочников (настройки)]]) — по-прежнему место **редактирования** полей самого агента (код, название, резидент, активен, «наша компания»).
- `/agents` и `/agents/{id}` — **просмотр и аналитика**: список агентов с индикатором «пора на валютный контроль», и карточка агента с договорами и аналитикой по каждому.

Договоры заводятся прямо на карточке агента (`POST /agents/{id}/contracts`, только Руководитель) — не через общий CRUD-реестр справочников, который рассчитан на плоские однотабличные структуры, а не на вложенный список «агент → договоры».

## Модель данных

Новая таблица `agent_contracts` (`app/models/agent_contract.py`), 1:N к `Agent`:
```python
class AgentContract(Base, TimestampMixin):
    id: int
    agent_id: int            # FK agents.id
    number: str
    start_date: date
    end_date: date | None    # NULL = бессрочный/действующий
    currency_control_registered: bool  # default False — поставлен ли ИМЕННО ЭТОТ договор на контроль
```

`PaymentRequest` и `PaymentTermsProposal` получили `contract_id`/`proposed_contract_id` (nullable — для прямых платежей без агента и для 54 исторически перенесённых заявок, у которых договор не зафиксирован) и `commission_includes_vat: bool | None`, заполняется Исполнителем на том же шаге, где вводится сумма комиссии ([[00a. Согласование условий исполнения (Платёж)|согласование условий исполнения]]). При принятии условий (`accept_terms`) оба поля копируются из предложения в саму заявку — как и остальные согласованные условия.

**Выбор договора в форме согласования условий — плоский список**, без JS-фильтрации по уже выбранному агенту (сама форма и так нигде не использует зависимые списки): каждый вариант подписан `<код агента> — № <номер договора>`, с «⚠» у договоров, не поставленных на контроль. Это сознательное упрощение первой версии, не ошибка.

## Аналитика (А1/А2) — в разрезе договора

`app/services/agent_analytics.py`. «Выплачено» = по заявке есть хотя бы одна запись `PaymentExecution` — это момент, когда деньги реально ушли, а не момент, когда заявка дошла до статуса «Закрыта» (между этим ещё идут проверка документов и согласование Руководителя, для валютного контроля уже не имеющие значения).

- **А1 (оборот)** — сумма `PaymentRequest.amount` по валютам + рублёвый итог. Рублёвый итог берётся из уже зафиксированного `PaymentExecution.amount_rub` (BR-061/062/091), а не пересчитывается заново по курсу — он точнее и не дублирует уже посчитанное.
- **А2 (вознаграждения)** — `agreed_commission_amount`, переведённый в рубли (курс `rate_at_execution`, если есть, иначе `rate_at_request`), раздельно по `commission_includes_vat`: с НДС / без НДС / не указано. Третья категория существует намеренно — чтобы на карточке агента сразу было видно, по скольким заявкам это поле забыли заполнить, вместо того чтобы тихо приплюсовывать их к одной из двух сумм.
- Обе выводятся прямо на карточке `/agents/{id}`, по каждому договору отдельно — отдельного экрана с фильтром по периоду в этой версии нет (можно добавить позже как ещё один [[Отчётность|отчёт]], если понадобится историческая динамика, а не только «на сейчас»).

**Известное ограничение:** если по заявке нет курса ни на дату исполнения, ни на дату заявки (бывает у перенесённых исторических записей), её сумма не включается в рублёвый итог — карточка договора в этом случае помечает итог как заниженный («не все суммы удалось сконвертировать»), а не молча показывает неверное число.

## БР-131. Пороги валютного контроля — на уровне договора

Оба порога проверяются только когда `AgentContract.currency_control_registered = false`, накопленная сумма считается запросом «на лету» (не хранимым счётчиком — см. обоснование в предыдущей редакции этого файла, актуально и для договора).

- **Порог 1 — 2 800 000 ₽.** Проверяется в `action_confirm_execution` (`app/main.py`), сразу после того, как зафиксированы `rate_at_execution` и `PaymentExecution.amount_rub` — это момент, когда запись об исполнении этого конкретного платежа становится полной.
- **Порог 2 — 2 900 000 ₽.** Проверяется в `action_propose_terms`, сразу после создания предложения условий: (уже выплачено по договору) + (планируемая комиссия этой заявки, переведённая в рубли по предложенному курсу).
- **Решение (подтверждено пользователем):** только уведомление, без блокировки — сохранить условия с этим агентом/договором можно и после срабатывания порога.

Срабатывание пишется в [[Аудит|аудит]] — `CURRENCY_CONTROL_THRESHOLD_TRIGGERED`, `entity_type="agent_contract"`, с суммой и номером договора в тексте.

## Уведомление — навязчивый баннер

Реализовано как общий для всех: `render()` в `app/main.py` на каждой странице (всем, у кого есть `can_view_analytics`, то есть Руководитель и все Исполнители) вычисляет список договоров, где контроль не поставлен и накопленная сумма достигла порога 1 (`agent_analytics.get_triggered_contracts`), и `base.html` рисует сплошную красную полосу сверху с перечислением каждого такого договора и ссылкой на карточку агента. Крестика «скрыть» нет — полоса пропадает только когда Руководитель отмечает договор как поставленный на контроль (`/agents/{id}/contracts/{contract_id}/toggle_currency_control`).

**Отличие от первой версии ТЗ:** там баннер адресовался «Руководителю и ответственному Исполнителю» (конкретно тому, кто ведёт эту заявку). Вычислить «ответственного именно за договор» (не за заявку — у договора таких заявок может быть несколько, с разными исполнителями) потребовало бы отдельной сущности или допущения, которого не было в постановке. Сознательное упрощение: баннер видят все с доступом к аналитике, а не только «ответственный» — на масштабе компании (50–100 заявок) это не создаёт шума, которого стоило бы избегать отдельным таргетингом.

## Что не реализовано

- Исторические 54 заявки не привязаны ни к одному договору (`contract_id = NULL`) — договоров на момент их переноса не было в системе; при необходимости можно проставить вручную через редактирование заявки (BR-018).
- Нет формы редактирования/удаления уже созданного договора (только добавление и переключение `currency_control_registered`) — если номер или даты договора введены с ошибкой, править пока только напрямую в БД.
- Нет отчёта с разбивкой по периодам (помесячно/поквартально) — только текущий накопленный итог.
