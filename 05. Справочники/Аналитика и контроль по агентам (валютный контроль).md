# Аналитика и контроль работы с агентами (валютный контроль)

> Источник: поставлена пользователем (Сергеем) в чате. Статус: ❌ не реализовано, не для первой версии — см. [[Агенты#Планы на будущее|Агенты → Планы на будущее]] и [[Заметки на будущее]].
> Ниже — техническое задание, достаточно детальное для реализации без дополнительных уточнений (модель данных, формулы, где именно проверять, формулировки уведомлений). Открытые вопросы, требующие решения Руководителя до начала работы, отмечены явно.

## Часть A. Аналитика по агентам

Два отчёта (по аналогии с существующими [[Отчётность|базовыми отчётами]] — BR-090/091, `app/services/reports.py`), за период, с выбором конкретного агента или по всем сразу:

**A1. Оборот платежей через агента.** Сумма платежей (`PaymentRequest.amount`), прошедших через агента — отдельно как Агент первого уровня (`agent_id`) и как Субагент (`subagent_id`), т.к. по [[Словарь предметной области#Маршрут исполнения платежа|маршруту исполнения]] это разные роли одной и той же записи справочника. В разрезе валют и в пересчёте в рубли (курс на дату исполнения — `PaymentExecution.rate_at_execution`, если заявка исполнена; на дату заявки — если ещё нет). Фильтр по статусу (все / только исполненные).

**A2. Суммы вознаграждений, выплаченных агенту.** Сумма `agreed_commission_amount` (поле уже есть в `PaymentRequest`, см. [[00a. Согласование условий исполнения (Платёж)|согласование условий исполнения]]) по заявкам, где агент выступал в этой роли, статус — исполнена/закрыта. **Отдельно с НДС и без НДС** — см. ниже про новое поле `commission_includes_vat`, которого в модели сейчас нет.

### Нужное изменение модели для A2 и для части B
В `PaymentTermsProposal` и `PaymentRequest` (точка фиксации — та же, что у `agreed_commission_amount`) добавить:
```python
commission_includes_vat: Mapped[bool | None] = mapped_column(nullable=True)
```
Заполняется Исполнителем при согласовании условий исполнения (туда же, где сейчас вводится сумма комиссии) — без этого поля отчёт A2 не сможет разделить суммы на «с НДС» / «без НДС», а просто взять одну фиксированную ставку НДС для всех агентов нельзя (часть агентов — нерезиденты, НДС к ним может не применяться вовсе, см. `Agent.is_resident`, уже в модели).

## Часть B. Контроль постановки агентского договора на валютный контроль

### Модель данных
Новое поле в `Agent` (справочник, [[Агенты]]):
```python
currency_control_registered: Mapped[bool] = mapped_column(nullable=False, default=False)
```
«Поставлен ли агентский договор с этим агентом на валютный контроль» — редактируется там же, где остальные поля агента (см. [[Администрирование справочников (настройки)]], когда реализовано; до этого — напрямую в БД/через будущую форму редактирования справочника агентов).

### Накопленная сумма вознаграждений агенту — не отдельное поле, а запрос
Накопленную сумму выплаченных агенту вознаграждений (в рублях, на любой момент) считать «на лету» запросом (`SUM(agreed_commission_amount` по заявкам, где `agent_id = X` или `subagent_id = X`, статус — исполнена/закрыта, с пересчётом в рубли по курсу на дату исполнения), а не хранить как отдельное накопительное поле на `Agent`. На объёме ~50–100 заявок (см. [[Реализация vs Описание#16. Интерфейс списка заявок|масштабирование]]) это дёшево, а хранимый накопительный счётчик рискует разойтись с реальностью при редактировании/удалении заявок задним числом (Руководитель теперь может и то, и другое — [[Бизнес-правила#BR-018. Удаление и редактирование любой заявки Руководителем|BR-018]]).

### BR-131. Два порога контроля (оба — только когда `currency_control_registered = false`)

**Порог 1 — 2 800 000 ₽, «накопленный».** Проверяется в момент, когда платёж агенту фактически исполнен — то есть там же, где сейчас пишется `PaymentExecution` (`confirm_execution`, после подтверждения). После записи исполнения пересчитать накопленную сумму вознаграждений этому агенту (см. выше); если она **достигла или превысила** 2 800 000 ₽ и `currency_control_registered = false` — сработало предупреждение (см. «Уведомление» ниже).

**Порог 2 — 2 900 000 ₽, «упреждающий».** Проверяется при подготовке новой заявки, в момент выбора агента на шаге [[00a. Согласование условий исполнения (Платёж)|согласования условий исполнения]] (там, где сейчас вводится `agreed_commission_amount`/`proposed_...`) — т.е. до фактической выплаты, на этапе планирования. Если **(накопленная сумма уже выплаченных вознаграждений этому агенту) + (сумма вознаграждения, предлагаемая в этой заявке)** ≥ 2 900 000 ₽ и `currency_control_registered = false` — сработало предупреждение.

**Открытый вопрос (решить до реализации):** срабатывание порога 2 — это только уведомление, или ещё и блокировка (нельзя сохранить условия с этим агентом, пока договор не поставлен на валютный контроль)? Пользователь попросил именно «уведомлять», не «запрещать» — реализовывать как уведомление без блокировки, если явно не попросят иначе при реализации.

### Уведомление — «очень навязчиво»
Обычного flash-сообщения (как для всех остальных предупреждений в системе) недостаточно — пользователь отдельно подчеркнул, что оповещение должно быть навязчивым. Конкретно:
- **Постоянный баннер**, а не разовое сообщение: пока по сработавшему агенту не выставлено `currency_control_registered = true`, баннер показывается **на каждой странице** (как шапка `base.html`) Руководителю и ответственному — т.е. Исполнителю, который предложил/ведёт условия исполнения по этой заявке (`req.executor_id`), не только в момент срабатывания. Баннер явно называет агента и то, какой порог сработал (2 800 000 — уже выплачено / 2 900 000 — с учётом планируемой заявки).
- Баннер не должен скрываться простым крестиком до конца сессии — либо не имеет кнопки «скрыть» вообще, либо кнопка скрывает его только до следующего захода (session-based, не постоянно).
- Срабатывание порога пишется в [[Аудит|аудит]] — новый тип события `CURRENCY_CONTROL_THRESHOLD_TRIGGERED`, `entity_type="agent"`, чтобы было видно, когда именно это обнаружилось, а не только видно текущее состояние баннера.
- Как только Руководитель отмечает `currency_control_registered = true` — баннер по этому агенту пропадает для всех; это тоже действие, которое стоит аудировать (`FIELD_CHANGE` на справочнике, см. `REFERENCE_UPDATED` — уже есть после [[Администрирование справочников (настройки)]]).
