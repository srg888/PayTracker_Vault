# Реализация vs Описание

> Сверка кода репозитория [[PayTracker]] (ветка `main`, коммит `3bf0423` — автофильтр по колонкам в списке заявок + слияние с BR-017, Исполнитель создаёт заявки и получает доступ к аудиту/отчётам/настройкам) с документацией Vault.
> Дата сверки: 17.10.2026. Полный повторный проход по всем разделам кода и docs (предыдущая версия сверки, коммит `9f105fc`, обновлялась точечно после каждой фичи — итоговая сводка и список расхождений ниже отставали от детальных таблиц; в этой редакции они пересчитаны заново и приведены в соответствие с детальными таблицами разделов 1–16).

## Легенда

- ✅ — реализовано полностью / соответствует описанию
- 🟡 — реализовано частично или с отклонениями от описания
- ❌ — не реализовано / отсутствует в коде
- ❓ — в описании открытый вопрос (не баг)

## 1. Роли и доступ ([[Роли и права]], [[Матрица прав]])

| Пункт описания | Статус | Где в коде / комментарий |
|---|---|---|
| Роли: Руководитель, Исполнитель, Заказчик | ✅ | `UserRole` в `app/models/enums.py` (RUKOVODITEL / ISPOLNITEL / ZAKAZCHIK) |
| Проверка прав на сервере, а не в UI (ADR-003) | ✅ | каждый POST-endpoint в `app/main.py` проверяет роль/статус/принадлежность; `TransitionError` ловится в `_do_transition` |
| **Делегированный руководитель**: Исполнитель с полномочиями Руководителя | ✅ | `is_acting_rukovoditel()` в `app/services/roles.py` — учитывает активное делегирование |
| Авторизация по сессии (без пароля) | ✅ | `login/{user_id}`, `app/security.py` |
| Неактивный пользователь (is_active) | ✅ | `User.is_active`; неактивный не входит в систему (BR-002), не назначается, не может взять заявку |
| Заказчик видит только свои заявки (`requester_id`) | ✅ | `requests_list` фильтрует `requester_id == user.id` для ZAKAZCHIK; то же в экспорте списка |
| Исполнитель и Руководитель видят все заявки | ✅ | без фильтра |
| «Создать заявку от имени Заказчика» (BR-015) | ✅ | поле «Заказчик» в форме (Руководитель/делегат/Исполнитель — см. BR-017), `requester_id` из формы, аудит `CREATED_FOR_REQUESTER` (old/new). Кнопка «+ НОВАЯ ЗАЯВКА» доступна всем ролям |
| Исполнитель может создавать заявки (BR-017) | ✅ | `can_create_as_executor` в `new_request_form`/`create_request`; ранее (BR-010–015) это было правом только Заказчика/Руководителя/делегата — расширено позже тем же изменением, что открыло аудит/отчёты/настройки (см. ниже) |
| Просмотр аудита, отчётов, настроек — Руководитель, делегат и **все** Исполнители (BR-017) | ✅ | `_require_analytics_access` в `app/main.py` (заменила точечные `_require_rukovoditel` на `/audit`, `/reports*`, `/settings*`); управление делегированием осталось только за `_require_rukovoditel` — не расширено |
| Удаление и редактирование любой заявки — только Руководитель (BR-018) | ✅ | `/requests/{id}/delete`, `/requests/bulk_delete`, расширенный `_require_editable_draft` в `app/main.py`; строго `_require_rukovoditel` — делегату недоступно (в отличие от BR-017). Аудит: `REQUEST_DELETED` (с дублированием номера/типа/статуса/автора/заказчика текстом — у `audit_log` нет FK на `requests`), `MANAGER_EDITED_REQUEST` + `FIELD_CHANGE`. Перед удалением физически подчищаются файлы документов с диска |

## 2. Жизненный цикл и статусы ([[Статусы заявки]], [[01. Жизненный цикл заявки]])

Статусная машина в `app/services/status_machine.py` реализует все переходы из описания.

| Переход | Статус | Комментарий |
|---|---|---|
| Черновик → Новая заявка (подача) | ✅ | `submit` |
| Новая → В работе (назначение Руководителем) | ✅ | `assign_executor` |
| Новая → В работе (сам, без назначения) | ✅ | `self_assign` (BR-023) |
| Новая → Отклонена → Архив («Ознакомлен») | ✅ | `reject`, `acknowledge_rejection` |
| Новая ⇄ Уточнение (до назначения) | ✅ | `request_clarification` разрешает NEW; `answer_clarification` возвращает в прежний статус (BR-042) |
| В работе ⇄ Уточнение | ✅ | то же |
| В работе → Условия предложены (только Платёж) | ✅ | `propose_terms` проверяет `req.payment_details` |
| Условия предложены → В работе (принять/отклонить) | ✅ | `accept_terms`, `reject_terms` (отклонение — с обязательным комментарием) |
| В работе → Ожидает подтверждения Заказчика | ✅ | `mark_execution_done` |
| Ожидает подтверждения → Проверка комплектности | ✅ | `confirm_execution` (неотменяемое, пишется в аудит) |
| Проверка комплектности → На проверке у Руководителя | ✅ | `confirm_documents_complete` (проверяет наличие обязательных документов — BR-050/051) |
| На проверке → Закрыта (только Руководитель) | ✅ | `manager_close` (BR-110) |
| На проверке → Проверка комплектности (доработка) | ✅ | `rework_from_manager` с обязательным комментарием (BR-111) |
| Каждый переход пишется в историю и аудит | ✅ | `RequestStatusHistory` + `AuditLog` (BR-041, BR-070) |
| Прямая установка статуса минуя машину невозможна | ✅ | статус меняется только через `_record` внутри переходов |

**Полнота статусной модели** — статусы совпадают с [[Статусы заявки]] один-в-один (11 статусов, включая `TERMS_PROPOSED` и `MANAGER_REVIEW`).

## 3. Создание заявки ([[00. Создание заявки]], [[01. Поля заявки — Платёж]])

| Пункт | Статус | Комментарий |
|---|---|---|
| Черновик при создании (BR-010) | ✅ | `status=RequestStatus.DRAFT` |
| Редактирование только своего черновика (BR-011) | ✅ | `_require_editable_draft` (`created_by == user && status == DRAFT`) |
| Неизменяемость поданной заявки (BR-012) | 🟡 | редактирование недоступно после подачи (роут `/edit` работает только для DRAFT); аудит изменений полей (old/new) по заявке **есть** — `_audit_field_change`/`FIELD_CHANGE` (предыдущая версия этой строки была не актуализирована, см. раздел 12). Нереализованной остаётся только отдельная «процедура изменения существенных параметров» уже поданной заявки |
| Номер заявки уникален и не через COUNT (BR-013, ADR-005) | ✅ | `_next_request_number` на базе `req.id` |
| Автор = Заказчик по умолчанию (BR-014) | ✅ | `requester_id = user.id` |
| Создание от имени Заказчика (BR-015) | ✅ | реализовано (см. раздел 1); доступно Руководителю, делегату и Исполнителю отдела; кнопка «+ Новая заявка» — для всех ролей |
| Выбор способа оплаты только Руководителем/Исполнителем, не Заказчиком (BR-016) | ✅ | `_can_choose_payment_method`; скрыто в `request_new.html` для Заказчика, проверка продублирована на сервере в `create_request`/`edit_request_submit` (BR-051-стиль, не только в UI) |
| **Поля «Платёж»**: сумма, валюта, реквизиты получателя, назначение, способ | ✅ | `PaymentRequest` в `app/models/request.py`; форма `request_new.html` |
| Курс ЦБ на дату заявки + сумма в рублях (инфо) | ✅ | `get_rate_for_today` + `_rub_amount` при создании; кэш по дате в `exchange_rates` |
| Edge case: cbr.ru недоступен → устаревший курс / предупреждение | ✅ | `get_rate_for_today` возвращает `(rate, is_stale)`; flash-предупреждение; фоновая повторная попытка — **есть** (см. ниже) |
| **Курс на дату исполнения** фиксируется отдельно | ✅ | в `confirm_execution` → `rate_at_execution`, `amount_rub_at_execution` |
| Лимиты файлов: 50 Мб/файл, 500 Мб всего, 50 файлов, форматы | ✅ | `MAX_FILE_SIZE`, `MAX_TOTAL_SIZE`, `MAX_FILES`, whitelist + libmagic |
| Фоновая повторная попытка получения курса | ✅ | `_background_rate_updater` + `lifespan`/`asyncio.create_task` — часовой фоновый джоб (предыдущая версия этой строки была не актуализирована) |
| Поля «Закупка» (компания-покупатель, способ, дата поставки) | ✅ | `PurchaseRequest` |
| Поля «Консультация» (описание вопроса) | ✅ | `ConsultationRequest` |
| Подразделение заказчика (юрлицо) | ✅ | `division_id` |

**Расхождение с [[ER модель|ER-моделью]]: `INTERNAL_SERVICES`.** ER-модель описывает службы-получателей как отдельную нормализованную таблицу-справочник с FK из `DOCUMENT_TYPES`. В коде это денормализованное строковое поле `DocumentType.recipient_service` (см. раздел 15) — функционально BR-123 закрыт, но без отдельного редактируемого справочника служб и без FK-целостности. Архитектурное отклонение от ER-модели, не критичное для текущего масштаба (внутренний инструмент, 50-100 пользователей).

**Устаревшая пометка в самой [[ER модель|ER-модели]].** Файл по состоянию на коммит `3447586` всё ещё содержит абзац «Не реализовано в коде. Маршрут исполнения (Агент+Субагент), срок исполнения в условиях, признак "наша компания" у Агента, `INTERNAL_SERVICES` и колонка "Служба-получатель" — на момент этой правки описаны только здесь…» (добавлен коммитом `386ed6` до того, как эти поля появились в коде). С коммита `33a2375` (код) эта пометка неверна для Агент+Субагент, срока исполнения и «наша компания» — они реализованы (см. раздел 6). Актуален только пункт про `INTERNAL_SERVICES` (см. выше). **Рекомендация: обновить или удалить этот абзац в ER-модели**, чтобы не вводить в заблуждение при следующей сверке.

## Крупнейшие расхождения (приоритет для доработки)

На момент этой сверки (код `3191203`, vault `3447586`) открытых пунктов немного — большая часть ранее найденных расхождений закрыта в последних 8 коммитах кода. Актуальный список:

### 1. Документы — два пункта из «Заметок на будущее» не реализованы
- Обязательное подтверждение «документ не нужен» при закрытии заявки (альтернатива загрузке).
- Предупреждение/чек-лист об отправке готовых документов заинтересованным лицам (Заказчик, ЦОБ ВЭД).
См. раздел 7 и раздел «Заметки на будущее — статус» ниже.

### 2. Неизменяемость поданной заявки (BR-012) — частично
Редактирование после подачи заблокировано (роут `/edit` работает только для статуса «Черновик»), но отдельной «процедуры изменения существенных параметров» для уже поданной заявки, о которой говорит BR-012, в коде нет — если такая потребность возникнет, менять поля можно будет только через отклонение/доработку с нуля.

### 3. История назначений исполнителя (BR-022, ADR-007) — через аудит, не отдельная сущность
Переназначения видны в `AuditLog`/`RequestStatusHistory`, но нет отдельной таблицы «кто исполнял с какого по какое число» — восстановление истории требует выборки по аудиту, а не прямого запроса.

### 4. Служба-получатель документа (BR-123) — закрыто функционально, но справочник не нормализован
`DocumentType.recipient_service` — строковое поле, не отдельная таблица (в отличие от ER-модели, где это `INTERNAL_SERVICES`). Сам перечень служб в документации всё ещё помечен как предварительный, подлежащий проверке у бухгалтерии/Руководителя (это открытый организационный вопрос, не технический долг). См. разделы 14–15.

### Ранее закрытые расхождения (для истории, не требуют действий)
Согласование условий платежа (субагент, срок исполнения, службы-получатели, условный комплект документов по маршруту — BR-100–123), создание заявки от имени Заказчика (BR-015), выбор способа оплаты только Руководителем/Исполнителем (BR-016), аудит входа/выхода и изменений полей (BR-071), фоновая повторная попытка получения курса ЦБ (`_background_rate_updater`), фактическое исполнение как отдельная сущность `PaymentExecution` (BR-080/081/082), вся аналитическая отчётность (базовые отчёты, суммы, просрочка, SLA, уточнения, полная история заявки) и импорт справочников из CSV — всё это закрыто и подтверждено в разделах 1–11, 14 выше.
