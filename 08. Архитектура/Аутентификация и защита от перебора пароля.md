# Аутентификация и защита от перебора пароля

> Статус: ✅ реализовано (код `srg888/paytracker`, коммит `e156803` — включает доработки по разбору DeepSeek поверх первой версии `f40b972`). Заменяет прежний вход без пароля (выбор пользователя из списка на `/login` — был прямо назван MVP-заглушкой в `AGENTS.md`). Повод — подготовка к внешнему доступу к PayTracker из интернета (не только из локальной сети/VPN).

## Доработки по итогам независимого разбора (DeepSeek)
Первая версия (`f40b972`) получила ревью от DeepSeek, который нашёл четыре реальных недочёта — три из них исправлены в `e156803`:
- **Блокировка по аккаунту целиком была DoS-уязвимостью на единственного Руководителя** — зная/угадав его email, можно было держать его без доступа бесконечно, с любого IP, просто повторяя по одной неверной попытке сразу после истечения очередной блокировки. Исправлено: блокировка теперь считается по паре (аккаунт, IP) — новая таблица `login_attempts` (append-only, как и остальной аудит в проекте, не мутируемый счётчик). Поля `User.failed_login_count`/`locked_until` из первой версии удалены как ошибочный дизайн.
- **`require_login` не проверял `is_active` на каждый запрос** — деактивация пользователя не действовала до истечения уже открытой 8-часовой сессии. Исправлено: проверка на каждый запрос, с принудительным завершением сессии при обнаружении.
- **IP в аудите (`LOGIN`/`LOGIN_FAILED`) был IP реверс-прокси, не реального клиента** — `uvicorn` без `--proxy-headers` не читает `X-Forwarded-For`. Добавлено `--proxy-headers` + `--forwarded-allow-ips` (обязательно вместе — без ограничения доверенных IP кто угодно мог бы подделать себе в аудите любой IP, подключившись напрямую). Порт приложения в `docker-compose.yml` теперь bindится на `127.0.0.1`, не `0.0.0.0` — снаружи сервера недоступен, только через реверс-прокси. **Значение `FORWARDED_ALLOW_IPS` по умолчанию (127.0.0.1) не гарантированно верно для реальной сетевой топологии — проверить при деплое.**
- Четвёртый пункт (посев паролей — ручной и блокирующий доступ между пересборкой контейнера и посевом) — не баг, сознательный trade-off, но `seed_passwords.py` дополнен запасным режимом без интерактивного терминала (переменная `SEED_PASSWORDS_JSON`) для случаев, когда `docker exec` идёт без `-it`.

## Что было не так (контекст)
Вход был `GET /login/{user_id}` — страница показывала список всех пользователей системы, клик по любому входил без единой проверки. При внешнем доступе это означало: любой, кто откроет `/login`, одним кликом получает права Руководителя — может удалять заявки (BR-018), видеть все финансовые данные, снимать валютный контроль (BR-131). Список пользователей на экране входа был отдельной утечкой — сразу видно, кто Руководитель, даже не пытаясь войти.

## Модель
`User` получил одно новое поле:
- `password_hash: str | None` — хеш argon2id (`argon2-cffi`). **NULL = пароль не задан, вход невозможен** — это не то же самое, что «пароль пустой»; пустых паролей не бывает.

Блокировка после перебора считается не полями на `User` (так было в первой версии, оказалось ошибкой — см. ниже), а отдельной append-only таблицей `login_attempts` (`user_id` nullable — попытка логируется, даже если email не совпал ни с одним пользователем; `ip`; `success`; `created_at`). Блокировка — не хранимое состояние, а каждый раз считается заново по этому журналу (в духе остального аудита в проекте).

Почему argon2id, а не bcrypt: текущая рекомендация OWASP для новых систем — за счёт требовательности к памяти устойчивее к атакам перебором на GPU/ASIC, чем bcrypt (который требователен только к процессору).

## Вход (`app/services/auth.py`, роуты в `app/main.py`)
- `POST /login` принимает email + пароль. **Одно и то же сообщение об ошибке** на все случаи провала (нет такого email, деактивирован, пароль не задан, заблокирован, неверный пароль) — иначе форма входа сама подсказывает атакующему, какие email вообще существуют в системе (user enumeration), что в компании из нескольких человек почти равносильно списку сотрудников.
- Блокировка нарастающая и **по паре (аккаунт, IP)**, не по аккаунту целиком: первые 4 неудачные попытки подряд с одного IP на один аккаунт — без последствий, дальше 1 → 5 → 30 → 60 → 240 минут, считается заново каждый раз по журналу `login_attempts` (не хранимый счётчик). Расписание — `LOCKOUT_SCHEDULE_MINUTES` в `auth.py`, менять можно прямо там, миграция не нужна.
- Каждая попытка (успешная и неудачная, даже если email не найден — тогда `user_id = NULL`) — запись в `login_attempts`; дополнительно каждая неудачная — отдельная запись в [[Аудит|аудит]] (`LOGIN_FAILED`, с IP), чтобы она была видна и там же, где остальная история действий пользователя.

## Смена и сброс пароля
- Пользователь меняет свой пароль сам — `/account/change_password` (ссылка «// ПАРОЛЬ» в шапке), требует знания текущего пароля.
- Сбросить пароль **другому** пользователю может только Руководитель — через 🔑 в [[Администрирование справочников (настройки)|справочнике «Пользователи»]] (`POST /settings/references/users/{id}/reset_password`), по аналогии с [[Бизнес-правила#BR-018. Удаление и редактирование любой заявки Руководителем|BR-018]] (административное действие, не рабочее). Пароль сообщается человеку устно/в мессенджере — рассылки email в системе нет и не планировалась.

## Переходный период — обязательный шаг после деплоя
После применения миграций (`ac5eacaf1219` → `fe9c70459079`) у всех существующих пользователей `password_hash = NULL` — **никто не может войти**, пока пароли не заданы. Это намеренно (открытый доступ без пароля не должен оставаться доступным ни секундой дольше необходимого), но значит: **сразу после деплоя нужно вручную запустить** `python -m scripts.seed_passwords` — интерактивный скрипт (или, без TTY, через `SEED_PASSWORDS_JSON` — см. докстринг файла), ввод пароля через `getpass` (не в истории шелла, не в аргументах командной строки). Entrypoint контейнера это НЕ делает автоматически — такой шаг нельзя гонять при каждом перезапуске.

## Сессионная кука
`SessionMiddleware`: `https_only=True` при `ENVIRONMENT=production` (без этого кука уходит и по обычному http — при внешнем доступе риск перехвата по открытому Wi-Fi/прокси), `same_site="lax"` (не `"strict"` — сломал бы переход по ссылке на PayTracker из письма/мессенджера на первый заход), `max_age=8 часов` — автоматический разлогин по истечении сессии, раньше сессия не истекала вовсе.

## Что не сделано в этой итерации (сознательно, решение пользователя)
- **2FA (TOTP)** — отложено: по словам пользователя, сейчас это тестовая среда с узким кругом пользователей. Дёшево добавить позже (одна библиотека, одно поле в БД) — стоит вернуться к этому вопросу до того, как внешний доступ станет постоянным, учитывая, что в системе уже реальные договоры и обязательства по валютному контролю (173-ФЗ), а не тестовые данные.
- **Сетевой уровень** (отдельный поддомен не на домене VPN-инфраструктуры, allowlist по IP/VPN-туннель, WAF, fail2ban на уровне nginx) — это конфигурация сервера, не код в этом репозитории; см. отдельный промпт для разворачивания, если уже выдавался.
- Нет ограничения на повторное использование старого пароля при смене, нет требования к сложности пароля кроме минимальной длины (8 символов) — можно усилить позже, если понадобится.
