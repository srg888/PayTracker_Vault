# Масштабирование списка заявок

> Замеры выполнены на реальной БД (не оценка): первый блок — в транзакции с откатом на проде, сквозные блоки — на отдельной временной БД в прод-контейнере. Продакшен-данные не изменялись. Дата: 2026-10-19, коммиты `3bf0423`, `648f05b`, `cc113d9`.

## Проблема

Список заявок (`GET /requests`, `requests_list` в `app/main.py`) устроен так:

```python
query = db.query(RequestModel)          # без LIMIT
requests_ = query.order_by(RequestModel.id.desc()).all()   # всё в память
```

Шаблон `requests_list.html` для каждой строки обращается к ленивым связям:
`r.requester`, `r.division`, `r.executor`, `r.payment_details`, `r.payment_details.currency`.
Каждое обращение — отдельный SQL-запрос. Это классическая проблема **N+1**: суммарно `N + 7` запросов.

## Замеры

| Заявок | SQL-запросов | Время рендера | С eager-загрузкой | С пагинацией 25 |
|---:|---:|---:|---:|---:|
| 100 | 107 | 105 мс | 1 запрос / 33 мс | 1 запрос / 24 мс |
| 500 | 507 | 488 мс | 1 запрос / 72 мс | 1 запрос / 32 мс |
| 1000 | **1007** | **946 мс** | 1 запрос / 122 мс | 1 запрос / **33 мс** |

Время — только серверный рендер на локальной БД. По сети к PostgreSQL будет хуже.

## Отсутствующие индексы

У таблицы `requests` есть только два индекса: `pk_requests (id)` и `uq_requests_number (number)`.
Индексов на `requester_id`, `status`, `executor_id`, `division_id`, `expected_date` **нет**.

План запроса списка для Заказчика (фильтр по `requester_id`):

```text
Sort  (cost=27.69..27.69 rows=1 width=121)
  Sort Key: id DESC
  ->  Seq Scan on requests  (cost=0.00..27.68 rows=1 width=121)
```

То есть `Seq Scan` — полный перебор таблицы даже при выборке заявок одного Заказчика.

## Предел без пагинации (полный сквозной замер)

Замер полного пути `GET /requests`: HTTP-запрос → SQL → рендер шаблона → HTML.
Выполнено в прод-контейнере против временной БД с полной схемой и демо-справочниками
(прод не затрагивался). Лучшее из трёх последовательных запросов, один процесс uvicorn.

| Заявок | Запросов к БД | Время ответа | Размер HTML |
|---:|---:|---:|---:|
| 100 | 108 | 119 мс | 100 КБ |
| 500 | 508 | 520 мс | 419 КБ |
| 1000 | 1008 | 1003 мс | 817 КБ |
| 2000 | 2008 | 2124 мс | 1,6 МБ |
| 5000 | 5008 | 5360 мс | 4,0 МБ |
| 10000 | 10008 | **11440 мс** | 8,0 МБ |

Зависимость строго линейная: около **1 мс на заявку** на сервере и около **0,8 КБ HTML на заявку**.
Число запросов к БД — `N + 8` (ленивые связи на каждую строку).

### Клиентская сторона при 5000 заявок

| Действие | jsdom (медленнее браузера в 3–5 раз) | Оценка браузера |
|---|---:|---:|
| Загрузка и разбор 3,5 МБ HTML | 8306 мс | ~1,7–2,8 с |
| Открытие панели фильтра | 384 мс | ~80–130 мс |
| Применение фильтра | 170 мс | ~35–55 мс |
| Сброс фильтров | 30 мс | ~10 мс |

Сам автофильтр остаётся работоспособным и на 5000 строк — тормозит не он, а доставка
и разбор страницы.

### Практический вывод

Без пагинации страница остаётся комфортной примерно **до 300–500 заявок** (ответ до
0,5 с, HTML до 0,4 МБ). До **1000** заявок — терпимо (около 1 с, что уже заметно).
Свыше **2000** — ощутимые задержки (2 с и более), а на **5000+** страница практически
непригодна: 5 с ответа сервера, 4 МБ передачи и многомегабайтный HTML на каждое открытие.
Порог из раздела «Что делать сейчас» (около 500 заявок) подтверждается замером.

Важно: один и тот же пользователь, открывший список несколько раз подряд, занимает
единственный процесс uvicorn на всё время рендера — при 5000 заявках это блокировка
остальных запросов на секунды.

## Шаги 1–2 выполнены (коммит `cc113d9`)

**Шаг 1 — eager-загрузка.** `requests_list` грузит `requester`, `created_by`, `division`,
`executor`, `payment_details.currency` через `joinedload`. Число запросов к БД перестало
зависеть от объёма: было `N + 8`, стало **2**.

**Шаг 2 — индексы.** Миграция `d5e6f7a8b9c0` добавила индексы на `requests`:
`requester_id`, `created_by_id`, `executor_id`, `division_id`, `status`, `expected_date`.
До неё даже выборка заявок одного Заказчика шла `Seq Scan` по всей таблице.

Замер `GET /requests` до и после (прод-контейнер, одинаковая методика):

| Заявок | Было | Стало | Ускорение |
|---:|---|---|---:|
| 100 | 108 зап / 119 мс | 2 зап / 33 мс | ×3,6 |
| 500 | 508 зап / 520 мс | 2 зап / 133 мс | ×3,9 |
| 1000 | 1008 зап / 1003 мс | 2 зап / 283 мс | ×3,5 |
| 2000 | 2008 зап / 2124 мс | 2 зап / 983 мс | ×2,2 |
| 5000 | 5008 зап / 5360 мс | 2 зап / 2200 мс | ×2,4 |

Оставшееся время — уже не обращения к БД, а сериализация и рендер растущего HTML
(на 5000 заявок это 6,9 МБ). Дальнейшее ускорение возможно только через пагинацию,
а она требует одновременного переноса фильтрации на сервер (шаги 3–4, см. ADR-008).

Примечание: на проде сейчас всего 3 заявки, поэтому `EXPLAIN` там всё равно выбирает
`Seq Scan` — на таком объёме индекс объективно дороже. Индексы начинают работать
на сотнях строк.

## Поведение клиентского автофильтра

Автофильтр по колонкам (см. [[Отчётность#Список заявок — автофильтр по колонкам (реализовано)|Отчётность]]) работает целиком в браузере по уже отрисованным строкам. Замер на 1000 строках в jsdom (медленнее реального браузера примерно в 3–5 раз):

| Действие | jsdom | Оценка реального браузера |
|---|---:|---:|
| Размер HTML страницы | **564 КБ** | 564 КБ (качать по сети) |
| Парсинг страницы + исполнение JS | 1971 мс | ~400–600 мс |
| Открытие панели (построение списка значений по 1000 строк) | 387 мс | ~80–120 мс |
| Применение фильтра | 41 мс | ~10 мс |
| Сброс фильтров | 5 мс | ~1 мс |

**Вывод.** Сама фильтрация останется быстрой и на нескольких тысячах строк — она линейная и дешёвая. Деградирует другое: размер страницы (около 0,5 МБ на 1000 заявок; ~2,8 МБ на 5000) и время первой отрисовки.

## План решения

### Шаг 1. Eager-загрузка связей

Добавить в `requests_list` жадную загрузку вместо ленивых обращений:

```python
from sqlalchemy.orm import joinedload

query = (
    db.query(RequestModel)
    .options(
        joinedload(RequestModel.requester),
        joinedload(RequestModel.division),
        joinedload(RequestModel.executor),
        joinedload(RequestModel.created_by),
        joinedload(RequestModel.payment_details).joinedload(PaymentRequest.currency),
    )
    .order_by(RequestModel.id.desc())
)
```

Эффект: 1000 заявок — 946 мс → 122 мс (в 8 раз), 1000 запросов → 1. Трудоёмкость ~30 минут, риск нулевой.

### Шаг 2. Индексы

```sql
CREATE INDEX ix_requests_requester_id ON requests (requester_id);
CREATE INDEX ix_requests_status       ON requests (status);
CREATE INDEX ix_requests_executor_id  ON requests (executor_id);
CREATE INDEX ix_requests_division_id  ON requests (division_id);
CREATE INDEX ix_requests_expected_date ON requests (expected_date);
```

Убирает `Seq Scan` для выборки Заказчика и ускоряет отчёты ([[Отчётность]]). Трудоёмкость ~15 минут.

### Шаг 3. Серверная пагинация

`LIMIT`/`OFFSET` с сортировкой в SQL. 1000 заявок — 33 мс независимо от объёма данных.

### Шаг 4. Серверная фильтрация — **обязательна вместе с шагом 3**

Если ограничиться только пагинацией, а автофильтр оставить клиентским, получится **молчаливо неверное поведение**: пользователь видит 25 строк текущей страницы, открывает фильтр по колонке «Заказчик» — а в списке только те заказчики, которые случайно попали на эту страницу. Отфильтровать по заказчику, чьи заявки лежат на сороковой странице, будет невозможно. Это опаснее медленной работы, потому что выглядит как рабочий фильтр.

Правильный вариант при пагинации:

- фильтры применяются в SQL: `WHERE status IN (...) AND division_id IN (...)`;
- значения для выпадающих списков берутся с сервера через `SELECT DISTINCT` **по всей таблице**, а не из отрисованных строк;
- счётчик «Показано N из M» считает `COUNT(*)` с теми же условиями;
- визуально автофильтр не меняется — меняется только источник данных.

Трудоёмкость шагов 3–4 вместе: ~4–6 часов.

## Что делать сейчас

Шаги 1 и 2 — **выполнены** (`cc113d9`): число запросов к БД больше не растёт с объёмом,
список стал в 2–4 раза быстрее.
Шаги 3–4 (пагинация + серверная фильтрация) — отложены до момента, когда число заявок
превысит примерно 500; выполнять их нужно парой.

Промежуточный вариант без пагинации: добавить на страницу выбор «показать по 50 / 100 / все» и виртуализацию строк. Дешевле, но потолок — примерно 2–3 тысячи заявок.
