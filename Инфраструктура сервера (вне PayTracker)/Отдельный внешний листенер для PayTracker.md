# Отдельный внешний листенер для PayTracker (вне dokodemo-door)

> ⚠ Перед тем как добавлять новую внешнюю точку входа через этот nginx — сначала [[Критическая уязвимость nginx — nginx2root (19.11.2026)|пропатчить nginx2root]]. Нет смысла открывать новый публичный порт на уязвимом nginx.
>
> Этот раздел — намеренно вне нумерованной структуры проекта (00–09): это инструкция по серверной инфраструктуре (nginx, Xray, ufw), не по коду или бизнес-процессам PayTracker. Адресат — DeepSeek (или любой, кто патчит сервер). Контекст и обоснование — [[Аутентификация и защита от перебора пароля]] в основном разделе 08, раздел «План решения» и всё, что выше него. Прочитай тот файл целиком перед тем, как читать этот.

## Зачем это вообще нужно — два повода сразу, не только IP

1. **Исходная задача этой ветки работы** (с которой всё и началось): пользователь хочет открыть доступ к PayTracker снаружи — не только через VPN-туннель Xray. Сейчас PayTracker доступен ТОЛЬКО через туннель (порт `8449` снаружи закрыт `ufw`) — то есть внешнего доступа в прямом смысле ещё нет вообще, несмотря на всю проделанную работу по паролям.
2. **Попутное следствие**, вскрытое при развёртывании аутентификации: весь трафик к PayTracker идёт через `dokodemo-door` (прозрачный TCP-форвардер без PROXY protocol), поэтому `nginx`/приложение видят `remote_addr = 127.0.0.1` у всех без исключения — блокировка по паре (аккаунт, IP) выродилась в блокировку по аккаунту целиком (см. [[Аутентификация и защита от перебора пароля]]).

Один и тот же шаг решает обе задачи: **отдельный, напрямую открытый снаружи листенер nginx специально для PayTracker, не проходящий через `dokodemo-door`**. Когда nginx принимает соединение сам, напрямую — реальный IP клиента никуда не теряется, PROXY protocol вообще не нужен.

## Что НЕ рассматриваем (уже проверено и отклонено)
- **`sniffing` в Xray** — даёт домен (SNI/Host), не IP. Не решает задачу.
- **PROXY protocol через `dokodemo-door`** — этот inbound его не умеет отправлять в текущей схеме.
- **Переиспользовать `v.uk.remote-fitness.online`** (домен VPN-маскировки) для внешнего PayTracker — не стоит: чем больше обычных сервисов светится на домене, который маскирует VPN-инфраструктуру, тем выше шанс, что кто-то, исследуя этот хост, наткнётся и на одно, и на другое одновременно. PayTracker должен получить **отдельный домен/поддомен**, никак явно не связанный с доменом VPN.

## Что сделать

### 1. Новый поддомен + DNS
Завести отдельный поддомен (не `v.uk.remote-fitness.online` и не его производные) — например, что-то не намекающее ни на VPN, ни на «paytracker» в лоб (по тем же соображениям маскировки, что и у остальной инфраструктуры). A-запись на тот же сервер.

### 2. Новый порт, напрямую открытый в `ufw`
Выбрать свободный порт (список занятого на сервере: Xray inbound'ы `8445`/`8447`/`8449`, сайты nginx `8444`/`8446`/`8448`, teaPot — **проверь, `9200` или `12425`, в двух местах этого vault названы разные числа, перед началом работы сверь по факту** `ss -tlnp` или аналогично). Добавить правило `ufw allow <новый порт>/tcp` — именно этот порт должен быть разрешён **напрямую**, не через туннель.

### 3. TLS-сертификат на новый поддомен
Отдельный сертификат (Let's Encrypt/certbot, как и для остальных сайтов nginx на сервере — посмотри, как выпущены текущие, и сделай так же) — не переиспользовать сертификат `v.uk.remote-fitness.online`.

### 4. Новый `server` блок в nginx
Слушает новый порт напрямую (не `127.0.0.1`, а на всех интерфейсах — именно сюда и должен приходить внешний трафик), с TLS из п.3, проксирует на `127.0.0.1:8000` (тот же uvicorn, что и сейчас) — **с теми же заголовками**, что уже есть в существующем блоке для `127.0.0.1:8448` (посмотри его как образец: `proxy_set_header Host`, и главное — `proxy_set_header X-Real-IP $remote_addr;` / `X-Forwarded-For $proxy_add_x_forwarded_for;`, которые раньше тоже стояли правильно, просто `$remote_addr` на входе уже был `127.0.0.1`).

Старый путь (через `dokodemo-door` → `127.0.0.1:8448`) можно оставить работать параллельно — не обязательно его убирать этим изменением; если решите убрать после того, как новый путь проверен — это отдельный шаг, не делайте его в этом же заходе.

### 5. `app/main.py` / `docker-compose.yml`
`FORWARDED_ALLOW_IPS` сейчас — `127.0.0.1` (см. [[Аутентификация и защита от перебора пароля]]). Это и останется верным: оба nginx-листенера (старый через dokodemo, новый прямой) физически обращаются к uvicorn с хоста же `127.0.0.1` — правка в `docker-compose.yml`/`entrypoint.sh` **не требуется**, их трогать не нужно.

## Обязательный порядок работ (не отступать)
1. Бэкап конфигов **перед** любой правкой: nginx (весь `/etc/nginx/...`, как уже бэкапили при предыдущем развёртывании) и `ufw` (`ufw status numbered` в файл, на случай отката правил).
2. Правки делать добавлением нового (новый server-блок, новое правило ufw, новый сертификат) — не редактируя существующие блоки/правила для Xray, teaPot или других сайтов nginx.
3. После правки — **обязательно** проверить, что ничего из старого не сломалось, тем же способом, каким проверялось предыдущее развёртывание (см. [[Аутентификация и защита от перебора пароля]], таблица «Что сделано»):
   - teaPot (порт — см. п.2 выше, сверить перед началом) — отвечает;
   - Xray inbound'ы `8445`/`8447`/`8449` — живы, вход через VPN-туннель по-прежнему работает;
   - сайты nginx `8444`/`8446`/`8448` — отдают 200;
   - `v.uk.remote-fitness.online:443` — по-прежнему ведёт туда же, куда и раньше (другое приложение на `127.0.0.1:3000`), не задет.
4. Проверить новое: зайти в PayTracker через новый поддомен/порт снаружи (не из локальной сети сервера), сделать несколько попыток входа — убедиться, что в [[Аутентификация и защита от перебора пароля|аудите/`login_attempts`]] пишется **настоящий внешний IP**, а не `127.0.0.1`.
5. Если что-то из п.3 не проходит — откат конфигов из бэкапа немедленно, в vault — что именно сломалось и на каком шаге, не чинить по живому в этом же заходе.
