# Проверка комплектности и закрытие заявки

Финальный этап [[01. Жизненный цикл заявки|жизненного цикла заявки]]. Наступает после того, как Заказчик [[07. Подтверждение исполнения Заказчиком|подтвердил исполнение]] заявки (статус → `Проверка комплектности документов`, см. [[Статусы заявки]]).

Документы здесь **не загружаются заново** — они уже были загружены Исполнителем по ходу [[00. Исполнение заявки — обзор|исполнения заявки]]. Этот шаг — только проверка комплектности. Дополнительные закрывающие документы (например, полученные позже — в частности, при участии субагента) можно догрузить на любом из под-шагов ниже, вплоть до фактического закрытия.

## Что происходит
1. Система формирует чек-лист обязательных документов для данного вида заявки на основе [[Справочник типов документов]] (в зависимости от того, была это Закупка, Платёж через агента или Платёж через банк).
2. Система автоматически отмечает, какие типы документов уже загружены, и подсвечивает недостающие обязательные.
3. Исполнитель догружает недостающие документы (если условный документ ещё требуется) и нажимает "Отправить на проверку Руководителю" → статус `Проверка комплектности документов` → `На проверке у Руководителя`.
4. Руководитель (или его заместитель с делегированными полномочиями) проверяет комплект документов и принимает решение:
   - **закрыть заявку** → статус → `Закрыта`;
   - **отправить на доработку** — обязательно с комментарием о причине → статус → `Проверка комплектности документов`, заявка возвращается Исполнителю, который догружает недостающее/исправленное и повторно отправляет на проверку (п.3–4 могут повторяться).

## Правила (см. [[Бизнес-правила]])
- **BR-050.** Заявка не может быть закрыта, если отсутствует обязательный документ.
- **BR-051.** Все правила обязательности документов проверяются на сервере, а не только ограничениями интерфейса.
- **BR-052.** Для конкретной заявки может быть создано индивидуальное правило обязательности документа (Руководитель или его заместитель могут переопределить перечень обязательных документов по конкретной заявке, не трогая общий справочник) — такое правило содержит заявку, тип документа, значение обязательности, автора изменения, дату и причину.
- **BR-083.** Заявка закрывается только после: завершения исполнения → подтверждения результата (если требуется) → проверки обязательных документов → проверки Руководителем → выполнения прочих обязательных условий.
- **BR-110.** Заявка закрывается только решением Руководителя (или его заместителя с делегированными полномочиями), после того как Исполнитель отметил комплект документов готовым. Простого подтверждения комплектности Исполнителем недостаточно для закрытия.
- **BR-111.** Руководитель может вернуть заявку на доработку вместо закрытия; отправка на доработку обязательна с комментарием о причине и фиксируется в [[Аудит|аудите]]. Цикл `Проверка комплектности документов ⇄ На проверке у Руководителя` может повторяться неограниченное число раз.

`Закрыта` — терминальный статус, дальнейшие действия по заявке не выполняются, но заявка остаётся видимой в [[Отчётность|отчётах]] и [[Аудит|аудите]].

## Доработка (не реализовано): обязательное решение по каждому документу и подтверждение рассылки при закрытии

> Источник: [[Заметки на будущее]] — «При закрытии заявки обязательное требование подгрузить документ или подтвердить что он не нужен. В конце предупреждение, что все нужные документы надо отправить заинтересованным лицам: заказчик, ЦОБ ВЭД. Или явно указать, что отправка не требуется и комментарий почему не требуется.»
> Статус: ❌ не реализовано — см. [[Реализация vs Описание]], раздел 7 и таблицу «Заметки на будущее — статус».
> Ниже — техническое задание, достаточно детальное для реализации без дополнительных уточнений (имена полей, роутов, аудит-событий). Открытые вопросы, требующие решения Руководителя до начала работы, отмечены явно. После реализации — перенести BR-055 и BR-112 в [[Бизнес-правила]] и обновить [[Реализация vs Описание]].

### Часть A. Обязательное решение по каждому документу (BR-055)

**Проблема сейчас.** На шаге `Проверка комплектности документов` чек-лист (`missing_required_documents`, `app/services/documents.py`) просто показывает, какие обязательные типы документов не загружены. Единственный способ закрыть заявку без документа — чтобы Руководитель вручную выключил требование через `toggle_document_requirement` (`POST /requests/{id}/document_requirements/{code}/toggle`). Три проблемы: (1) доступно только Руководителю, хотя решение «документ не нужен» по факту принимает Исполнитель в процессе сборки комплекта; (2) не требует причины — `RequestDocumentRequirement` хранит только `is_required_override: bool`, без `reason`/`changed_by_id`/`changed_at`, хотя BR-052 это прямо требует (расхождение уже отмечено в [[Реализация vs Описание]]); (3) ничего не пишется в `AuditLog`.

**BR-055. Явное решение по каждому обязательному документу.**
Прежде чем Исполнитель сможет выполнить переход `Проверка комплектности документов` → `На проверке у Руководителя` (действие, аналогичное текущему "Отправить на проверку Руководителю"), по каждому типу документа, обязательному для маршрута этой заявки (с учётом условности по BR-122 — субагент, банк и т.п.), должно существовать одно из двух:
  a. загруженный файл (`RequestDocument` с этим `document_type_code`), либо
  b. явное решение «не требуется» с обязательным комментарием-причиной.
Если нет ни того, ни другого хотя бы по одному документу — переход запрещён на сервере (`TransitionError`), а не только скрыт в интерфейсе (в духе BR-051).

**Кто принимает решение «не требуется».** Исполнитель, назначенный на заявку, либо действующий Руководитель (`is_acting_rukovoditel`). Это расширяет действующее BR-052 (сейчас — право только Руководителя): решение принимается на рабочем, а не управленческом уровне, а управленческий контроль за ним всё равно обеспечен тем, что Руководитель проверяет итоговый комплект на шаге `На проверке у Руководителя` (BR-110) и может отправить на доработку, если не согласен (BR-111).
**Открытый вопрос:** подтвердить с Руководителем, что расширение права на Исполнителя приемлемо — альтернатива: оставить решение только за Руководителем, тогда Исполнитель может лишь предложить/запросить, а финальное решение принимается на шаге `На проверке у Руководителя`.

**Модель данных.** Расширить `app/models/document.py`, класс `RequestDocumentRequirement` (не заводить новую таблицу — те же поля закрывают и этот гэп, и существующее расхождение по BR-052):
```python
reason: Mapped[str] = mapped_column(Text, nullable=False)                               # НОВОЕ, обязательное
changed_by_id: Mapped[int] = mapped_column(ForeignKey("users.id"), nullable=False)       # НОВОЕ
changed_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now(), nullable=False)  # НОВОЕ
```
Миграция Alembic (autogenerate); для уже существующих строк (если есть) — `reason = "(причина не указана — запись создана до внедрения BR-055)"`, `changed_by_id = created_by_id` заявки.

**Роут.** Заменить `toggle_document_requirement` на `POST /requests/{request_id}/document_requirements/{doc_type_code}/waive` (`reason: str = Form(...)`, проверка `reason.strip()` непустой; доступ — Исполнитель заявки или действующий Руководитель) и `.../unwaive` (отмена решения, тоже с обязательной причиной). Обратный случай — пометить необязательный по умолчанию документ обязательным именно для этой заявки — остаётся правом Руководителя, можно оставить в том же роуте через параметр `is_required_override: bool` + обязательный `reason`.

**Аудит.** Новое значение `AuditActionType.DOCUMENT_REQUIREMENT_WAIVED` (и `DOCUMENT_REQUIREMENT_RESTORED` для отмены). Запись в `AuditLog`: `entity_type="request"`, `entity_id=request_id`, текст причины — либо через `request_document_requirements.reason` по ссылке, либо продублирован в `AuditLog.new_value` для чтения истории без join.

**UI.** В чек-листе документов на странице заявки — рядом с каждым недостающим обязательным документом две кнопки: «Загрузить» (как сейчас) и «Отметить, что не требуется» (открывает форму с обязательным полем причины). Если решение уже принято — бейдж «Не требуется (причина: …, кто: …, когда: …)» с возможностью отменить (тоже с причиной).

### Часть B. Подтверждение рассылки документов заинтересованным лицам (BR-112)

**BR-112. Подтверждение рассылки документов перед закрытием.**
На шаге `manager_close` (переход `На проверке у Руководителя` → `Закрыта`) Руководитель обязан явно подтвердить одно из двух, иначе переход завершается ошибкой (`TransitionError`), аналогично тому, как сейчас `rework_from_manager` требует непустой `reason`:
  a. комплект готовых документов отправлен заинтересованным лицам — Заказчику и в ЦОБ ВЭД, либо
  b. отправка не требуется, с обязательным комментарием-причиной.

**Кто такие «заинтересованные лица».** В заметке названы Заказчик и «ЦОБ ВЭД» — подразделение пока не описано в [[Словарь предметной области]].
**Открытый вопрос (решить до реализации):** (1) уточнить у Руководителя полное название и состав «ЦОБ ВЭД»; (2) нужен ли расширяемый справочник адресатов, или для первой версии достаточно двух захардкоженных получателей («Заказчик», «ЦОБ ВЭД»). Если список будет расти — переиспользовать паттерн [[Справочник типов документов|`DocumentType.recipient_service`]] (BR-123), а не заводить третий параллельный способ хранить «кому направить».

**Модель данных.** Новые поля в `Request` (правило не ограничено платежами, см. формулировку заметки):
```python
documents_sent_to_stakeholders: Mapped[bool | None] = mapped_column(Boolean, nullable=True)
documents_sent_comment: Mapped[str | None] = mapped_column(Text, nullable=True)
documents_sent_confirmed_by_id: Mapped[int | None] = mapped_column(ForeignKey("users.id"), nullable=True)
documents_sent_confirmed_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True), nullable=True)
```
(Если в будущем понадобится фиксировать подтверждение по каждому получателю отдельно — вынести в отдельную таблицу `request_document_dispatch_confirmations`; для первой версии полей на `Request` достаточно, т.к. в заметке речь об одном общем решении.)

**Роут/сервис.** `manager_close` получает два новых обязательных поля формы: `documents_sent: bool` и `documents_sent_comment: str = Form(...)` (комментарий обязателен в обоих случаях — «отправлено, куда именно» или «не требуется, почему»). В `app/services/status_machine.py`, функция `manager_close(db, req, user)` — принять эти параметры и провалидировать `comment.strip()` непустой до записи перехода в `CLOSED`.

**Аудит.** Новое значение `AuditActionType.DOCUMENTS_DISPATCH_CONFIRMED`, пишется той же транзакцией, что и `CLOSED_BY_MANAGER`.

**UI.** Кнопка «Закрыть заявку» (видна Руководителю на статусе `На проверке у Руководителя`) открывает форму: радио-кнопки «Документы отправлены» / «Отправка не требуется» + обязательное текстовое поле комментария; кнопка подтверждения закрытия неактивна, пока поле не заполнено.
